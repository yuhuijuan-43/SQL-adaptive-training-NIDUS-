# SQL 自适应学习平台 — 项目方案总览

> 本文件是项目的"AI Agent 参考手册"，汇总了所有调研结论、设计决策与技术选型，供后续开发过程中 AI 助手理解项目全貌和关键约束。

---

## 1. 项目定位

**一句话概括：** "自适应引擎 + 生成式 AI" 双引擎协同驱动的 SQL 刷题平台。正确时自适应平滑进阶，错误时 AI 生成同源变式题精准补弱，实现**千人千面、因错施教**。

**使用场景：** Web 端

**目标用户：**
| 用户类型 | 特征 | 需求 |
|---|---|---|
| 零基础转行小白 | 无 CS 背景，学习意愿强 | 从基础 SQL 语法开始，渐进式引导 |
| 计算机专业大学生 | 有学科基础 | 技能巩固、面试准备，有挑战性内容 |

---

## 2. 核心机制

### 双引擎协同

```
用户答题
  ├── ✅ 正确 → 自适应引擎主导 → 评估掌握度+正确率+历史轨迹 → 动态调整难度与进程
  │                              → 始终处于"最近发展区"(ZPD)
  │
  └── ❌ 错误 → 双引擎协同
                 ├── 第一步(自适应引擎): 精准归因
                 │   • 结合知识图谱分析错误根因
                 │   • 区分: JOIN逻辑错 / GROUP BY语法错 / 子查询混乱 / 聚合函数误用
                 │
                 └── 第二步(生成模型): 智能干预
                     • 基于错因动态生成"知识点同源、考察逻辑相似、数据场景全新"的变式题
                     • 实现"错一题，练一类"的靶向训练
```

### 用户完整旅程

```
注册 → 冷启动摸底 → 自适应主循环(答题→IRT/BKT更新能力值→引擎计算下一题→展示)
       ↓                                                    ↓
  身份标签 + 摸底测试 + 行为探测                     错题自动归集
                                                         ↓
                                                    同源变式题
                                                         ↓
                                                    学习数据报表
```

## 3. 关键技术方案

### 3.1 系统三核心模型

| 模型 | 职责 | 实现要点 |
|---|---|---|
| **领域知识模型** | 学习内容的"知识地图" | SQL 知识点拆解为细粒度，标明依赖/前置关系，以知识图谱呈现 |
| **学习者模型** | 用户的"数字画像" | 采集答题正误、耗时等行为数据，用 IRT/BKT 动态推断掌握程度 |
| **自适应引擎** | 系统的"决策中枢" | 实时更新画像 → 规划最优路径 → 推荐下一题及难度 |

### 3.2 用户画像建模

**核心算法：**
- **IRT (项目反应理论)** — 通过作答模式估计用户能力值 θ 和题目参数（难度、区分度、猜测系数）
- **BKT (贝叶斯知识追踪)** — 隐马尔可夫模型，追踪每个知识点的"掌握/未掌握"状态转移

**关键决策：** 选择 LightGBM 替代 MissForest（MissForest 复杂度太高），LightGBM 基于梯度提升、向斜率最大的方向优化。

### 3.3 冷启动策略

采用**组合策略**，而非单一方案：

| 策略 | 做法 | 适用阶段 |
|---|---|---|
| 身份标签选择 | 用户手动选择（零基础 / 有基础） | 注册时 |
| 初始摸底测试 | 覆盖各难度的诊断题（5-10 道） | 首次进入 |
| 轻量级行为探测 | 首几道题的正确率、耗时等 | 早期交互 |
| 先验注入 | 结合用户信息作为贝叶斯先验 | 建模初期 |
| Thompson 采样 | 前 3-5 题探索与利用平衡 | 建模初期 |

### 3.4 知识图谱

**定位：** 实现精准推荐的关键基础设施，表征 SQL 知识点间的关联与依赖关系。

**构建方式：** 自动抽取 + 专家校验 + 用户行为迭代优化

**工具选型：**

| 工具 | 定位 | 推荐场景 |
|---|---|---|
| Neo4j + LLM Builder | LLM 从非结构化文本自动提取实体关系 | 大量文档自动化建图 |
| Microsoft GraphRAG | LLM 提取，节点关系更稠密 | 高推理要求场景 |
| PostgreSQL 递归 CTE | 内建关系型方案 | **MVP 阶段推荐**（暂不引入 Neo4j，降低架构复杂度） |

### 3.5 数据库设计

**核心实体：**

| 表 | 职责 | 关键字段 | 增长特点 |
|---|---|---|---|
| Learner | 用户静态信息 | user_id, name, group, location | 平缓 |
| Content | 学习资源元数据 | content_id, title, difficulty, course_id, tags | 平缓 |
| Interaction | 用户行为日志 | user_id, content_id, action, timestamp, duration | **极快，性能瓶颈** |

**辅助表：** Learner Profile Extension、Content Hierarchy/Graph、Interaction Summary、Course/Module

**交互表技术选型：**

| 方案 | 写入性能 | 查询能力 | 推荐场景 |
|---|---|---|---|
| ClickHouse | 极高 | 极强，TB 级秒级聚合 | **首选**，漏斗分析、趋势统计 |
| Elasticsearch | 极高 | 强，毫秒级 | 实时日志分析、数据看板 |
| PostgreSQL | 适中 | 强 | 业务主库（Learner + Content） |

**MVP 推荐架构：PostgreSQL（主库）+ ClickHouse（交互分析）**

### 3.6 LLM 选型

**应用场景：** 生成同源变式题、错误分析与诊断、自然语言转 SQL、自动出题

| 模型 | 性能 | 速度 | 推荐场景 |
|---|---|---|---|
| **Qwen2.5-7B-Instruct** | ★★★☆☆ | 快 (~1-2s) | **轻量变式题生成、实时反馈** |
| DeepSeek-V3 | ★★★★☆ | 快 (~1.5-3s) | 高性价比生产部署 |
| Qwen2.5-72B-Instruct | ★★★★☆ | 中 (~3-6s) | 生产部署、数据敏感场景 |
| CodeLlama-34B | ★★★☆☆ | 中慢 (~4-7s) | SQL 语法修正 |
| GLM-4-Plus | ★★★★☆ | 中 (~2-4s) | 中文场景适配 |

### 3.7 学习理论支撑

| 理论 | 核心概念 | 在系统中的应用 |
|---|---|---|
| 认知负荷理论 | 工作记忆容量有限 | 动态平衡题目难度，防止认知过载或闲置 |
| 布鲁姆分类法 | 记忆→理解→应用→分析→评价→创造 | 知识点分层，按认知深度递进规划路径 |
| 学习风格理论 (VARK) | 视觉/听觉/读写/动觉 | 匹配不同媒介形式的呈现方式 |

## 5. 风险与应对策略

### 5.1 算法层（高优先级）

| 风险 | 应对策略 |
|---|---|
| **IRT/BKT 冷启动精度不足** | ① 先验注入（贝叶斯先验）② Thompson 采样快速收敛 ③ UI 附加"正在学习中"轻提示 |
| **LLM 生成变式题幻觉** | ① 生成-校验双通道（沙箱执行验证 SQL）② 人工抽检+众包标注 ③ 初期限定生成范围（模板化生成） |
| **知识图谱完整性缺失** | ① 自动抽取+专家校验 ② 用户交互数据动态迭代 |

### 5.2 工程层

| 风险 | 应对策略 |
|---|---|
| **LLM 推理延迟高（3-8s）** | ① 异步任务队列（Celery+Redis）+ WebSocket 推送 ② 轻量模型（Qwen2.5-7B）+ 量化加速 ③ 高频题目缓存池预生成 |
| **系统架构复杂** | ① 云原生托管服务降低运维 ② MVP 阶段裁剪：PostgreSQL CTE 替代 Neo4j，暂缓 ClickHouse |

### 5.3 数据层

| 风险 | 应对策略 |
|---|---|
| **交互数据稀疏性** | 个体建模优先（IRT/BKT + LLM），不依赖群体数据 |
| **数据隐私与合规** | 最小必要采集 + 脱敏加密 + 用户可导出/注销 |

### 5.4 体验层

| 风险 | 应对策略 |
|---|---|
| **"自适应"感知不强** | UI 解释推荐原因（如"这道题略难，因为你上次在 JOIN 上犯了个小错"）+ 成长曲线/雷达图可视化 |
| **挫败感与流失** | 情感保护机制：连续答错 3 题降难度 + 插入已掌握题"信心加固" |

## 9. 关键设计原则

1. **零依赖：** 所有页面输出为自包含 HTML，无外部构建步骤
2. **个体建模优先：** 初期不依赖群体协同过滤数据，IRT/BKT + LLM 即可工作
3. **渐进式架构：** MVP 阶段裁剪非核心组件（Neo4j → PostgreSQL CTE），降低初始运维负担
4. **可解释性：** 推荐逻辑对用户可见可感，提升信任度
5. **情感保护：** 算法层面嵌入防止挫败感的保护机制
