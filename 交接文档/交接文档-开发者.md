## 1 这是什么项目

一套用于 SQL 技能自适应训练的 Web 平台。学习者登录后进入"自适应进阶"模式：系统按知识图谱的固定顺序出题（每题 5 道：3 选择 + 2 填空），做对的知识点在知识图谱上"点亮"，进度一目了然；另有自主练习、真题池、错题集、水平诊断、管理后台等模块。

一句话产品定位：**SQL 版的 Duolingo**——按知识点组织题库，用"点亮图谱"替代"刷题计数"，让学习进度可视、可感知。

当前规模：练习池 **483 道题**（原 58 题精选 + 按知识标签分批扩充）、真题池 42 道牛客风格填空题（覆盖全部 29 个知识标签），完整题库备份 557 / 50 题。支持多用户、GitHub 一键登录、管理员多角色体系，并具备日志/备份/运行时数据治理等运维能力。

## 2 快速开始

```bash
# 方式一：Windows 一键启动（自动探测/安装 Python、装依赖、起服务、开浏览器）
start_server.bat

# 方式二：手动
pip install -r backend/requirements.txt -r backend/requirements-dev.txt
python backend/run.py            # 访问 http://localhost:5000

# 测试（178 用例）
cd backend && pytest -q
```

`run.py` 启动链：`init_db()` 建表并清理 WAL → `startup_maintenance()` 治理（清过期管理员会话）→ `backup_database()` 在线备份 → `seed_*()` 从 `data/` 灌库（条数不符才重建）→ waitress 起服务（`0.0.0.0:5000`）。退出时自动做 WAL checkpoint 并清理临时文件，异常残留由下次启动的 `_cleanup_stale_wal` 兜底。

## 3 技术栈

| 层 | 选型 | 理由/备注 |
|---|---|---|
| 后端 | Python + Flask 3.1 | 轻量，单文件可跑 |
| 数据库 | SQLite（WAL 模式） | 无部署成本；生产单进程多线程 |
| WSGI | waitress | Windows 下 gunicorn 不可用；多进程写 SQLite 增加锁争用，故单进程多线程 |
| 密码 | bcrypt | 旧 sha256:盐/明文格式登录时自动升级 |
| 限流 | Flask-Limiter（memory://） | 只限写接口/登录/admin |
| 第三方登录 | GitHub OAuth2 授权码 | 可选，环境变量或 json 配置 |
| 前端 | 原生 HTML/CSS/JS | 无框架无构建；ECharts/CodeMirror/Font-Awesome 全部本地化，可离线部署 |
| 测试 | pytest | 178 用例 |
| 一键部署 | `start_server.bat` + ngrok | Windows 场景 |

## 4 架构总览

```
                    ┌─────────────────────────────┐
   浏览器            │  Flask (app.py)              │
   frontend/*.html  │  路由 / 鉴权 / 限流 / 页面托管  │
   (原生JS)          └──────┬──────────┬───────────┘
      │                     │          │
      │ /api/* (JSON)       │ 数据访问  │ 业务逻辑
      ▼                     ▼          ▼
   before_request      repositories   engine(自适应/点亮)
   登录门槛+白名单        (纯SQL查询)    sql_judge(判题)
      │                     │          auth(认证)
      │                     ▼          oauth(GitHub)
      │                     │          logs(动态/系统日志)
      │                     ▼          maintenance(运行时治理)
      └─────────────►  SQLite (db.py, questions.db)
                      seeding.py 从 data/*.json 灌库
                      backup.py 在线备份到 backend/backups/
```

分层原则：**路由层薄、数据层厚**——`app.py` 只做参数解析、鉴权、响应组装；所有 SQL 在 `repositories.py`；算法（自适应/判题/点亮）独立成模块，可脱离 HTTP 单测。运维类逻辑（日志/备份/治理）独立成模块且**必须静默失败**，绝不阻断业务。

## 6 产品核心概念：知识图谱与自适应

### 6.1 知识图谱（7 大类 × 29 标签）

图谱是"学习地图"：根 → 7 个枝（DML / SELECT / 函数 / 子查询 / 表连接 / 约束 / DDL）→ 29 个叶标签（如 `select_basic`、`join_inner`、`window_func`）。每个标签有星级（★简单/★★中等/★★★困难），决定题目难度。结构权威定义在 `seeding.py:OFFICIAL_TAGS`（与 `data/knowledge_tags.csv` 呼应，但代码以硬编码为准）。

学习顺序由 `LEARNING_EDGES` 声明（如 `select_basic → where_basic`、`aggregate_func → group_by → having`），保留早期引擎的进阶路径。

### 6.2 自适应出题

"自适应"不是复杂推荐算法，而是一套**确定性的图谱遍历规则**：

- 一轮 = 按图谱固定顺序（DML → SELECT → 函数 → 子查询 → 表连接 → 约束 → DDL，枝内再按叶序），把所有**未点亮且还有题**的叶节点刷完。
- 每个叶节点出 5 题：3 选择题 + 2 填空题（选择先行）；题池不足时循环复用同一批题，填空池为空回退选择题池。
- 题目源白名单 `JOURNEY_SOURCES = ('static_basic','static_advanced','nowcoder_preview')`，排除历史牛客/LeetCode 全量题。

### 6.3 点亮规则（产品的灵魂）

| 层级 | 点亮条件 |
|---|---|
| 叶节点 | 满足任一：① 本轮连对 3 道且相邻提交间隔 ≤2min；② 本轮该叶 5 题全对；③ 跨池累计答对 **10 道不同的题** |
| 枝节点 | 该枝下全部叶点亮（x/y 显示进度） |
| 根节点 | 全部 7 枝点亮（x/7 显示进度） |

规则③是"慢热型"保障：即使一轮内表现不佳，持续正确练习也能点亮，避免挫败感。规则①②是"即时反馈"：一轮内表现好可以提前点亮并跳过剩余题。一轮结束后点亮状态保留，自动开新一轮。

> 2026-09-06 语义修正：规则③ 改为 `COUNT(DISTINCT question_id)`。因题池循环复用，旧实现下"同一题答对 10 次"即可点亮，与"掌握 10 道题"的意图不符。

### 6.4 掌握度模型（EWMA）

每答一题更新该题所属节点的掌握度：`ewma += 0.3 * (是否答对 - ewma)`（初值 0.5）。早期用贝叶斯 Beta(α/β)，但因缺少遗忘机制、早期错误会永久拖累掌握度，2026-08 迁移为 EWMA（`tools/migrate_ewma.py`），旧列保留不再更新。

## 7 后端模块详解

### 7.1 `app.py` — 主入口

- **页面托管**：`FRONTEND_DIR` 锚定项目根/frontend，各页面路由直接 `send_from_directory` 返回；`/lib/<path>` 服务本地化前端依赖。
- **API 全集**：诊断、刷题（questions/submit/derive/recommend）、图谱、journey、平台账号（login/register/logout/check-username）、OAuth、进度、admin（20 余个）。
- **登录门槛**：`before_request` 钩子，除 `_PUBLIC_API_PATHS` 白名单外所有 `/api/*` 需有效 `session_id`。**新加接口默认受保护**，若要公开必须显式加白名单。
- **限流**：写接口/登录注册/admin 用 flask-limiter 限流（详情见 AI 版 §8.4），读题不限流避免误伤正常用户。
- **admin 鉴权**：`Authorization: Bearer <token>` → `validate_admin_token` → `require_admin` 装饰器注入 `g.admin_username`。历史上曾用"共享密钥 + 自报 operator"，已被 C2 安全重构替换。
- **错误处理**：统一 JSON 返回；500 会写入 `system_logs` 供管理端查看。

### 7.2 `engine.py` — 自适应引擎（产品的核心）

- 状态机：每用户一行 `journey_state`，本轮进度存 `round_state` JSON（`entries/idx/pos/answers/lit_round`）。
- `journey_next` 是主入口：先登记本轮计划内题的作答（防陈旧提交污染）→ 判规则①③点亮 → 双 while 推进（本叶出完判规则② → 下一叶 → 一轮完成）。
- `compute_lights` 输出完整点亮状态（叶 lit/correct、枝 x/y、根 x/7），journey 与 status 接口共用；支持传入 `counts` 复用聚合结果，避免同请求重复查库。
- 常量集中可调：`STREAK=3`、`GAP_MAX=120`（秒）、`CORRECT_LIT=10`、`SEQ_TYPES=['mcq','mcq','mcq','fillin','fillin']`。

### 7.3 `sql_judge.py` — SQL 判题

设计决策：**主判题路径是"真实执行 + 结果集比对"，字符串规范化只是回退/快速路径**。理由：学员写法千变万化（别名、列序、等价表达式），字符串匹配必然误判；而内存 SQLite 执行零成本且安全（只读单语句白名单）。

- 安全校验：剥离注释 → 引号感知分句（`_split_statements`）→ 必须恰好 1 条且首关键字为 select/with/explain/pragma。
- 环境构建：用题目的 `table_schema` + `initial_data` 在 `:memory:` 建库，失败则回退字符串比对（兼容旧行为）。
- 比对规则：列数一致 + 行集 multiset 一致（列序/行序无关、保留重复行、float 整数与 int 归一、列名不参与）。
- 考察点限定：`required_points`（JSON）声明判题必须出现的构造，为空时从标准答案自动推导。
- 错误友好化：表不存在/列不存在/语法错误/聚合误用映射为中文提示。

### 7.4 `db.py` — 连接与 schema

- 连接：Flask 请求内复用 `g.db`（WAL + busy_timeout=5000），teardown 关闭；脚本场景独立连接。
- **20 张表**（见 AI 版 §5 全表）：题库 2、图谱 3、学习数据 4（progress/mastery/journey/lights）、账号 5（users/admin_users/password_history/referral_codes/admin_sessions）、运维 3（activity_log/system_logs/schema_meta）、其他 3（admin_settings/diagnostic_results/derived_questions）。
- **增量迁移模式**：新增列用 `ALTER TABLE ... ADD COLUMN` 套 `try/except: pass`（幂等），不重建表。`users.last_active`、`admin_users.personal_key` 是现成先例；`schema_meta.schema_version` 记录当前结构版本。

### 7.5 `repositories.py` — 数据访问层

路由不直接拼 SQL 的"厚数据层"。重点函数：`save_answer`（答题落库 + 同步更新 `user_mastery` 的 EWMA + 触发治理保险丝）、`get_graph`（进程内缓存，种子变更需 `invalidate_graph_cache`）、`reset_user_password` / `rollback_user_password`（密码历史 3 条）、`delete_user` / `delete_admin`（级联清理关联数据，单事务）、`get_progress`（按池 JOIN 不同表，规避 id 串扰）。

### 7.6 `auth.py` — 认证与账号体系

- 平台用户：bcrypt 存储；用户名白名单 `^[\w一-龥]{2,32}$`（防管理页 XSS）；密码 8-64 字符；会话 90 天不活跃过期（`last_active`）+ 显式登出立即失效。
- 管理员：内推码注册（默认码 `NIDUS_Agent` 在引导期——库里尚无管理员时——种入一次，最后一条不可删）；登录/注册签发 `admin_sessions` 会话 token（30 天 TTL，绑定身份）。**个人密钥（一人一钥）已于 2026-09-03 移除**：门禁只校验账号密码。
- 实时监控（2026-09-03）：`logs.py` 新增 `activity_log`（kind=user/admin）与 `system_logs`；普通管理员可查用户动态与系统日志，主管理员额外可见管理员动态；两个表都有封顶留存（1.2 万 / 5 千条），不会随用户量无限膨胀。
- 主管理员权限：管内推码、删管理员、改/回退管理员密码；普通管理员只能重置平台用户密码。

### 7.7 `oauth.py` — GitHub 登录

- 配置优先级：环境变量 > `oauth_config.json`（gitignore，仅本地）。
- 流程：state 存 Flask session 防 CSRF（`hmac.compare_digest` + 单次使用）→ 刻意不传 redirect_uri（用 GitHub 注册回调，规避 mismatch）→ 按 `github_id` 查/建用户。
- 用户名冲突策略：原名 → `_gh` → `_ghNN` → uuid 后缀；GitHub 账号密码为随机 bcrypt（不可密码登录，管理员可重置）。并发双回调由唯一索引 + IntegrityError 改查兜底。

### 7.8 `seeding.py` — 题库与图谱种子

- 从 `data/questions.json`（483 题）与 `data/exam_questions.json`（42 题）灌库，**库内条数不符时先备份再清表重建**；`OFFICIAL_TAGS` / `TAG_STARS` / `TAG_DIFFICULTY` / `LEARNING_EDGES` / `CATEGORY_TO_TAG` 定义图谱结构。
- 改图谱结构（增删标签）是高风险操作：要同步改 `OFFICIAL_TAGS`、`knowledge_tags.csv`、题库 category 字段，并留意测试对节点数的断言。
- 扩充题库不改此文件，走 `tools/import_questions.py`（入库 + 同步 JSON，保持条数一致避免触发重建）。

### 7.9 运维三件套

| 模块 | 职责 | 设计要点 |
|---|---|---|
| `logs.py` | 用户/管理员动态、系统日志 | 写入静默失败；每次写入后惰性裁剪到封顶条数；字段长度截断 |
| `backup.py` | 启动/重建/导入前在线备份 | 用 SQLite 在线备份 API（不依赖文件复制）；保留最近 N 份（`DB_BACKUP_KEEP`，默认 20） |
| `maintenance.py` | 长驻服务的运行时治理 | 保险丝式：`user_progress` 超阈值才压缩重复答对行（保答错行/首条答对/最近 30 条）；`admin_sessions` 过期清理 |

## 9 部署与运维

### 9.1 本地启动
`start_server.bat`（自动探测/安装 Python 3.13、装依赖、起服务、开浏览器）或手动 `python backend/run.py`。

### 9.2 公网访问（课堂/演示场景）
仓库带 `ngrok/` 二进制。**OAuth 回调唯一性**：GitHub OAuth App 只支持一个回调 URL，部署后必须同步改 GitHub 应用回调与本地启动地址，否则授权回调指回 localhost。

### 9.3 配置与密钥
- OAuth：环境变量 `GITHUB_OAUTH_CLIENT_ID/SECRET`（服务器推荐）或 `backend/oauth_config.json`（本地双击 bat 场景），两者均不入库。
- `FLASK_SECRET_KEY`：设了才能让 Flask session cookie（OAuth state）跨重启稳定。
- `FLASK_DEBUG=1`：仅限本机调试（Werkzeug 调试器暴露网络可致 RCE）。
- 数据治理阈值：`USER_PROGRESS_MAX_ROWS`（默认 100000）、`USER_PROGRESS_CHECK_EVERY`（默认 500，0 关闭）；备份份数 `DB_BACKUP_KEEP`（默认 20）。

### 9.4 数据备份与恢复
- 题库可重建（`data/*.json` → seeding），**不入库**；用户数据在 `backend/questions.db`。
- 自动备份：每次启动/题库重建/批量导入前由 `backup.py` 落一份到 `backend/backups/`，保留最近 20 份（每份约 11MB，满额约 220MB，注意磁盘占用）。
- 迁移到新机器：装依赖 → 拷仓库（含 `questions.db` 则用户数据随迁；不含则自动重建题库）→ 启动。

### 9.5 长驻运行的增长控制
长驻服务（部署到网站）很少重启，因此治理逻辑不能只挂在启动时：`user_progress` 保险丝挂在每次答题入库后（计数达标才查行数，超阈值才压缩），`admin_sessions` 过期清理挂在管理员登录时，日志表每次写入后惰性裁剪。详见 AI 版 §5.1。

## 10 题库管理

### 10.1 数据文件

| 文件 | 说明 |
|---|---|
| `data/questions.json` | 练习池当前源（**483 题**） |
| `data/exam_questions.json` | 真题池当前源（42 题） |
| `data/batches/` | 批次扩充题源（b2/b3/b4 按知识标签分文件） |
| `data/questions_batch1.json` | 第 1 批扩充题源（50 题，留档） |
| `data/leetcode_questions.json` / `leetcode_parsed.json` | LeetCode 原始题面 / 解析素材（各 105 题） |
| `data/questions_full.json` / `exam_questions_full.json` | 完整备份（557/50），仓库保留 |
| `data/knowledge_tags.csv` | 29 标签难度映射（Windows 下中文星级显示乱码，代码以 `OFFICIAL_TAGS` 为准） |
| `data/basic_select.csv` / `advanced_select.csv` | 人工编写题库原始稿 |

### 10.2 题目格式（详见 `docs/format_spec.md` 与 `docs/sample/`）

选择题：`options` 用 `|` 分隔（SQL 连接符 `||` 有转义保护），配 `option_explanations`，`correct_answer` 必须与某一项文本一致；判对用双向 HTML 实体归一。填空题：`table_schema`（CREATE TABLE）+ `initial_data`（INSERT）+ `correct_answer`（标准 SQL）+ `expected_output`。新增题 `category` 必须是 29 官方标签之一（旧分类可用 `CATEGORY_TO_TAG` 映射），`difficulty` 必须与标签星级一致，`q_level` 由难度推导（easy→basic，其余→advanced）。

### 10.3 扩充流程（推荐）
1. 题库素材写入 `data/batches/*.json`（或由 `tools/leetcode_*.py` 从 LeetCode 生成）。
2. `python tools/import_questions.py <批次文件> --check`：校验类别/难度一致性、选项格式、填空题标准答案实判通过、与现有题不重复。
3. `--import`：自动备份 DB → 入库并写 `question_knowledge` → **同步追加 `data/questions.json`**（保持与库内条数一致，避免下次启动触发重建）。

> ⚠️ 不要手工直接改 `questions.json` 的题数：条数与库内不符会触发全库重建，并清理对不上 id 的练习答题记录。

### 10.4 工具脚本
`tools/import_questions.py`（批次导入）、`convert_question_bank.py`（HTML 备份 → JSON，硬编码本机路径）、`verify_exam_bank.py`（真题校验）、`crawl_leetcode.py` / `leetcode_convert.py` / `leetcode_build*.py`（LeetCode 建题链）、`gen_required_points.py`、`scan_*`（解析残留扫描）、`migrate_ewma.py`、`rename_sources.py`、`db_stats.py`。

## 11 安全设计要点

项目经历过一轮正式安全审计（`docs/安全审计记录.md`），要点：

1. **C2 重构**（已修复）：管理鉴权从"共享密钥 + 自报 operator"改为"per-admin 会话 token 绑定身份"，杜绝普通管理员伪装主管理员。
2. **服务端重算**（已修复）：诊断成绩不信任客户端自报，服务端重判。
3. **判题沙箱**：只读单语句白名单 + 内存库执行，防写库。
4. **登录门槛**：所有 `/api/*` 默认需登录（白名单除外）。
5. **密码策略**：bcrypt、用户名白名单防 XSS、密码历史可回退、90 天会话过期 + 显式登出。
6. **遗留待处理**：CORS 放行 `null` 来源（file:// 打开 admin 页的取舍，建议统一走 Flask 托管）；**默认内推码 `NIDUS_Agent` 已随仓库公开**（建议部署后由主管理员删除并建立私密内推码流程）。

## 12 开发规范与约定

- **分层**：路由层薄、数据层厚；新 SQL 进 `repositories.py`，不进路由。
- **迁移**：schema 变更用 `db.py` 的 `ALTER TABLE` try/except 模式，不重建表；重大变更同步 `schema_meta.schema_version`。
- **测试**：改后端必须跑 `pytest`；新功能配测试（判题测原子函数、API 测 client、鉴权测 Bearer 语义）。
- **注释**：中文注释 + 函数 docstring；改动留日期注释（如 `2026-09-06`）便于追溯。
- **不可破坏路径**：`seeding.py` 数据路径（`__file__` 相对）、`app.py::FRONTEND_DIR`、`start_server.bat::%~dp0`、`tests/test_seed_rebuild.py` 路径——移动文件必须同步改。
- **判题语义**：主判题是结果集比对，字符串比对仅回退；别动只读首关键字白名单。
- **运维逻辑必须静默失败**：日志/备份/治理异常绝不阻断业务主流程。
- **性能**：`get_graph()` 有进程内缓存，改种子后要 `invalidate_graph_cache()`；单进程多线程写 SQLite，别引多进程。
- **敏感信息**：OAuth 密钥、`.mcp.json`、`server_path.conf` 不入库不写文档。

## 13 已知问题与后续方向

1. **备份磁盘占用**：`backend/backups/` 每份约 11MB、最多囤 20 份（约 220MB），内容高度重复；可考虑压缩存储或减少保留份数。
2. **文档治理**：`docs/` 下内部文档（新人接手指南、自适应算法指引、安全审计记录、modification.md、汇报讲解稿）被 gitignore 仅本地保留，建议决定是否转正入仓或迁移 wiki，避免交接断档；其中 `新人接手指南.md` 已过时（描述早期 BKT 三阶段算法与 `database.py`），需重写或归档。
3. **格式规范合并**：`docs/题目格式规范.md` 与 `docs/format_spec.md` 内容重叠，建议合一并定唯一权威源。
4. **LLM 变式题**：早期规划"答错时 LLM 生成同源变式题"，现状只有"选择题自动转填空题"（`derived_questions`），可扩展。
5. **部署材料**：尚无 Dockerfile/正式部署文档，只有 Windows bat + ngrok；对外演示建议补生产部署说明。
6. **CORS null 来源**：见 §11 遗留项，建议评估移除。
7. **继续扩题**：练习池已达 483 题，仍可继续按官方 29 标签扩充（尤其稀缺标签），全量备份 557/50 题在 `data/` 可回溯。
8. **答题历史归档**：`user_progress` 有保险丝兜底，但真正的长期归档（如按学期导出/清理）尚未实现。
9. **动态流降噪**：答题事件占比极高，管理端动态流容易被"答题"刷满，可考虑按事件类型过滤或聚合展示。
